# Machine Learning Design Document

## 1. Introduction

This document defines the latest machine learning architecture for the Smart Streetlight Automation and Predictive Maintenance System.

The ML layer runs in the FastAPI backend and consumes telemetry from ESP32-based streetlight nodes connected via Wi-Fi.

## 2. ML Objectives

- Detect electrical anomalies in near real time
- Predict failure risk before hard outages
- Support maintenance prioritization (`low`, `medium`, `high`)
- Reduce downtime and reactive maintenance cost

## 3. ML Problem Framing

### 3.1 Problem Types

- **Classification:** Fault state prediction
- **Anomaly Detection:** Behavior outlier detection
- **Time-Series Forecasting:** Degradation and failure trend estimation

### 3.2 Target Outputs

- Fault class / anomaly flag
- Failure probability score (`0.0` to `1.0`)
- Maintenance urgency level (`low`, `medium`, `high`)

## 4. Data Inputs

### 4.1 IoT Source

Data is generated by ESP32 nodes with LDR, voltage, and current sensors.

### 4.2 Required Telemetry Fields

| Field | Type | Description |
| :--- | :--- | :--- |
| `node_id` | String | Unique node identifier |
| `timestamp` | DateTime (ISO8601) | Measurement timestamp |
| `light_level` | Float | Ambient light reading from LDR |
| `voltage` | Float | Voltage reading |
| `current` | Float | Current reading |
| `power` | Float | Computed electrical power |
| `relay_state` | Boolean | Lamp relay state |
| `device_status` | String | Device health state |

### 4.3 Optional Derived Features

- `voltage_fluctuation`
- `current_deviation`
- `power_trend`
- `operating_hours`
- `fault_frequency`

If not provided by IoT firmware, these are computed in the backend feature pipeline.

## 5. Feature Engineering

### 5.1 Raw Features

- `voltage`, `current`, `power`, `light_level`
- `relay_state`
- `device_status` (encoded)

### 5.2 Engineered Features

- Rolling mean/std windows for electrical values
- Delta features (`d_voltage`, `d_current`, `d_power`)
- Runtime and fault-count context
- Windowed sequences for LSTM input

## 6. Data Preprocessing

- Missing value handling and range validation
- Noise smoothing for unstable sensor series
- Scaling (`StandardScaler` for RF/SVM, sequence scaler for LSTM)
- Label encoding for categorical features
- Train/validation/test split with time-awareness

## 7. Model Set (Latest)

### 7.1 Random Forest

- **Purpose:** Failure classification
- **Library:** Scikit-learn
- **Input:** Snapshot + engineered features
- **Output:** Predicted class and confidence/probability

### 7.2 Support Vector Machine (SVM)

- **Purpose:** Anomaly detection / separation of normal vs abnormal patterns
- **Library:** Scikit-learn
- **Input:** Normalized electrical behavior features
- **Output:** Anomaly flag and decision score

### 7.3 LSTM

- **Purpose:** Time-series failure/degradation forecasting
- **Library:** TensorFlow or PyTorch
- **Input:** Ordered telemetry windows
- **Output:** Future failure trend score / time-to-failure proxy

## 8. Training Strategy

- Initial offline training from historical `streetlight_logs`
- Periodic retraining using newly collected telemetry
- Versioned model artifacts with tracked metrics
- Promote model versions only after metric validation

## 9. Evaluation Metrics

### 9.1 Random Forest / SVM

- Accuracy
- Precision
- Recall
- F1-score
- ROC-AUC (where applicable)

### 9.2 LSTM

- MAE
- RMSE
- Trend direction accuracy

## 10. Inference and Alert Flow

1. Backend receives telemetry from `node_id`.
2. Data is validated and persisted.
3. Feature pipeline transforms current + recent history.
4. RF/SVM/LSTM inferences run.
5. `PredictiveMaintenance` is updated.
6. Alert rules evaluate thresholds and model outputs.
7. Dashboard reflects latest status and urgency.

## 11. Maintenance Urgency Logic

- **Low:** No anomaly, low failure probability
- **Medium:** Degradation trend or moderate risk detected
- **High:** Confirmed anomaly and/or high failure probability

## 12. Deployment and Operations

- ML inference is served inside FastAPI services.
- Model artifacts are loaded on startup and reloaded on version update.
- Inference logs and metrics are tracked for model monitoring.

## 13. Retraining Lifecycle

- Scheduled retraining (monthly/quarterly or on data drift)
- Version control of artifacts and metrics
- Rollback support to previous stable model version

## 14. Limitations

- Early-stage labeled fault data may be imbalanced
- Sensor quality and calibration impact prediction quality
- Long-horizon forecasting accuracy depends on telemetry density

## 15. Future Enhancements

- Edge pre-filtering/inference on ESP32
- Traffic/weather-enriched features
- Adaptive thresholding from seasonal patterns

## 16. Conclusion

The latest ML architecture aligns with the current ESP32 + Wi-Fi + electrical sensor system and uses a three-model strategy (Random Forest, SVM, LSTM) for anomaly detection and predictive maintenance.
